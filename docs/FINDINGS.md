# Findings

Results live in [`../results/SUMMARY.md`](../results/SUMMARY.md), generated by
`python -m bench.report` from raw run output. This file records findings that are
not a result table: corpus facts, licence constraints, and failure modes.

## Status

No scored run has been committed yet. The harness is complete and the corpus is
pinned; what is missing is a local model run, which is measured in hours because
PageIndex indexes 34 documents through an LLM in local mode. Until that run
exists, this file contains no accuracy claims.

## Corpus findings

These were established while building the corpus and are independent of any run.

### The comparison point is unlicensed

`VectifyAI/PageIndex-OSS-Benchmark` publishes the curated 62-question benchmark
over 34 documents, and it is the natural thing to compare against. It has no
LICENSE file; the GitHub API returns 404 for its `/license` endpoint. No licence
means all rights reserved.

Its underlying annotations, however, descend from `MMLongBench-Doc`, which is
Apache-2.0. This is what makes the re-derivation possible.

### The derivation is exact

Filtering `MMLongBench-Doc-V2`'s `samples.json` to the 34 documents used by the
comparison point yields **284 questions**, of which the curated 62 are a strict
subset. Restricting further to questions whose `evidence_sources` is
`['Pure-text (Plain-text)']` yields **90 questions** containing **all 62**
curated questions verbatim.

Verified by exact match on `(doc_id, normalised question text)`: **62 of 62**.

| Set | Rule | n |
| --- | --- | --- |
| `full_284` | `doc_id` in the 34 documents | 284 |
| `comparable_90` | `doc_id` in the 34 documents **and** pure plain-text evidence | 90 |
| `curated_62` | the comparison point's own selection | 62 |

The consequence is that results on the 62-question subset can be compared
directly against published figures, while the 222 extra questions in `full_284`
are scored too — a scope the comparison point does not cover.

## Published comparison point

From `VectifyAI/PageIndex-OSS-Benchmark`'s `results.json` (62 questions, 34
documents, local mode, flash indexing). Numbers are cited; no file from that
repository is reproduced here.

| Chat model | Reasoning effort | Accuracy | Cost/question |
| --- | --- | ---: | ---: |
| `gpt-5.6-luna` | none | 85.5% | $0.003081 |
| `gpt-5.6-luna` | medium | 91.9% | $0.003806 |
| `gpt-5.6-luna` | high | 96.8% | $0.003607 |
| `gpt-5.6-terra` | medium | 98.4% | $0.030322 |
| `gpt-5.6-sol` | medium | 100% | $0.081008 |

Read this carefully. Accuracy rises with model cost by roughly an order of
magnitude per step, and the spread within a single family (85.5% → 96.8% for
`luna`) is larger than the gap between families. On a 62-question set the
binomial standard error alone is about ±4 points, so several of these steps are
not separable from noise.

What this table does **not** contain is a vector-RAG baseline. Every row is
PageIndex against itself. That is the gap this harness exists to fill.

## Findings: PageIndex local mode on a small local model

Discovered by running the harness rather than by reading the SDK. These are the
most transferable results so far, and they are about *operating* vectorless RAG
locally, not about retrieval quality.

### The model has to bridge a name/id mismatch, and long filenames break it

PageIndex's local agent targets a document by putting its **name** into the
instructions it gives the model, then resolves its **tools** only by internal
`pi-` id. Measured directly:

| Identifier passed to `get_document` / `get_page_content` / `get_document_structure` / `document_context` | Result |
| --- | --- |
| `pi-f28537f944c744019ec2025831ed7377` | all four succeed |
| `a5879805d70c854ea4361e43a84e3bb2.pdf` | all four fail: `Document not found` |

So the model must reproduce a 36-character hex filename inside a tool call. With
`qwen3:8b` it does not: four attempts on one question returned

- `Document not found. Did you mean "a58798005d70c854ea4361e43a84e3bb2.pdf"?` (three times — note the extra `0`, i.e. the model's transcription is wrong)
- `Invalid page number: 14. The document has 15 pages, but page 14 is not valid.`

The same document was then ingested a second time as **`doc-01.pdf`**, and the
tool call succeeded immediately — it reached `get_page_content` for **page 14,
the correct evidence page**.

**Consequence.** Ingesting under a short deterministic name (`doc-01.pdf` …
`doc-34.pdf`) removes the model's weakest step without touching the document.
`PageIndexLocal.staged_name` implements this; the mapping is written to
`corpus/pageindex_store/staged_names.json` so a run is still reproducible.

**This matters for the benchmark's validity.** Before this change the harness was
measuring `qwen3:8b`'s ability to transcribe a filename, not PageIndex's
retrieval quality. Any comparison run without the fix would have been a
comparison of the wrong thing.

### The real cause: the agent loop terminates on a tool result

The envelope `chat()` returns is whatever the **last tool call** produced, not a
synthesised answer. Six distinct shapes, same question, same document:

| Envelope | What it actually is |
| --- | --- |
| `{"status":"success","content":"February 8, 2021"}` | a real answer (seen once, early) |
| `{"page":14,"text":"<page 14>"}` | the result of `get_page_content` |
| `{"success":true,"doc_name":"doc3.pdf","structure":[…]}` | the result of `get_document_structure` |
| `{"error":"Duplicate request for page 14…"}` | its own duplicate-call guard |
| `{"error":"Document not found…"}` | name/id resolution failure |
| `""` | empty |

This reframes the diagnosis. It is **not** primarily an identifier problem (that
was real and is fixed) and **not** primarily a token-budget problem. With
`qwen3:8b` the model keeps calling tools and never decides to stop and answer, so
the caller receives the last tool output. A frontier model ends the loop with a
final assistant message — which is why the vendor's published numbers do not show
this failure.

The harness handles this correctly: a page or structure payload yields its
retrieved pages as genuine provenance and is flagged `_shape`, never scored as a
response.

### Thinking mode costs 24x here, for no accuracy gain on this task

`qwen3` is a hybrid reasoning model and emits hidden reasoning by default.
Measured through the baseline adapter on the same question, same document, same
retrieved context — only the knob differs:

| `think` | Answer | completion tokens | Latency |
| --- | --- | --- | --- |
| on (default) | `2021-02-08` | 206 | **19.3 s** |
| off | `2021-02-08` | 11 | **0.8 s** |

Same correct answer, **24× faster**, 19× fewer output tokens. On a grounded
extraction task the reasoning buys nothing and costs almost everything — which
also means every latency figure quoted elsewhere in this file is a
thinking-enabled figure, and the baseline is far cheaper than it looks.

A second, nastier consequence: **a small output-token cap produces an empty
response**, because the model spends the entire budget reasoning and never emits
content. That is the origin of one of the empty answers observed above, and it is
the failure mode most likely to corrupt a result silently — no error, no warning,
just nothing.

It is a **knob, not a policy**. `PAGEINDEX_THINK` and `BASELINE_THINK` default to
**on**, because the upstream benchmark shows accuracy rising with reasoning effort
and a harder multi-hop question is exactly where it should pay off. Both adapters
take the same setting, so the two systems can be held identical on it — otherwise
this would become a silent confounder in the comparison. Turning it off is a
one-variable experiment with a one-command revert, not a permanent choice.

### What this says about local vectorless RAG

Running a reasoning-based retriever on a small local model moves the failure
surface. Retrieval itself worked whenever the loop got that far — the tree led to
the right page. The failures were in the *protocol around it*: reproducing an
identifier, selecting the right one among several documents, and above all
terminating the loop with an answer rather than a tool result. That is a different
class of problem from the one the vectorless-RAG pitch is about, and it is
invisible in any benchmark run on a frontier model.

The practical consequence for this repository: **the retrieval comparison is
measurable, the accuracy comparison is not** — not until the system under test can
produce an answer at all. Neither number appears here, because producing one from
a system that returns a tool payload or an empty string would be reporting the
harness's behaviour rather than the model's.

## Findings: the machine, not the code

### 16 GB is not enough to run the model and the database together

Measured on the development laptop (Apple M5, 16 GB) with PageIndex's store,
Ollama, Colima and the pgvector container all up:

```
vm.swapusage: total = 9216.00M  used = 7816.94M     (85% of swap in use)
swapins 50,184,166   swapouts 59,661,457
```

Resident at the same time: `qwen3:8b` 5.9 GB, `nomic-embed-text` 0.58 GB, the
Colima VM 3.0 GB, plus the OS and the harness. The result is that a **two-token
reply took 89 seconds** — every token pages model weights back off disk.

This is invisible in any test that does not run the whole system at once, and it
is the most likely explanation for the wildly variable PageIndex latencies
(52–59 s for a single question) recorded elsewhere in this file. Those numbers
are not a property of tree retrieval; they are a property of a machine that is
out of memory.

**Consequence for the benchmark:** latency measurements from this machine are not
comparable to anything, and should not be published. Accuracy measurements are
unaffected, but they need the model to be able to finish a call at all.

A smaller model does fit — `qwen3:1.7b` (1.4 GB) answered in **3.6 s** where the
8B model could not finish in 180 s. A workable local configuration exists; it is
just not the configuration that gives good answers.

### Page-addressed questions are structurally unfair to vector retrieval

Asking the document-assistant path *"What is the date mentioned on page 14?"*
with the small model:

- **Vector baseline**: retrieved pages 2, 3, 1, 3, 3 — **not page 14** — and
  answered `28/3/2018` against a reference of `2021-02-08`. Confidently wrong.
- **PageIndex**: retrieved **page 14** — correct — but returned the page text
  instead of an answer (see above).

The reason is not a flaw in either implementation. *"On page 14"* is a
**structural** constraint: it points at a location, not a meaning, and an
embedding of the question cannot represent it. Semantic search matched pages that
mention dates, which is the reasonable thing to do with the words it was given.

A tree index encodes the structure, so it can honour a page reference directly.
**This is a real, mechanical advantage of the vectorless approach, demonstrated
rather than asserted** — and it is the strongest evidence yet that the comparison
is worth making properly, because the question set contains a meaningful number
of page-addressed questions that quietly favour one side.

It also cuts the other way as a caution: the baseline answered fast and wrong,
with no signal that retrieval had missed. A document assistant built on this must
report its sources, which is why the harness and the CLI both do.

## Expected failure modes to look for

Recorded before the run so that post-hoc rationalisation is harder.

1. **Index refusal.** Flash indexing rejects some documents, especially
   scan-heavy ones. The comparison point's own practice is to exclude documents
   that fail to index rather than score them as failures, and it removed 11 of
   135 documents upstream. Coverage must be reported as a number, not silently
   dropped.
2. **Chart and figure questions.** A tree of text nodes cannot see an image.
   PageIndex's multimodal handling is a separate path and `full_284` is where a
   gap should appear if one exists.
3. **Multi-page evidence.** The wider set includes cross-page questions. Tree
   reasoning should handle these better than top-k chunks, since top-5 chunks
   must happen to span the right pages.
4. **Retrieval hit rate flat, accuracy differs.** If the two systems retrieve
   equally well but score differently, the difference is in generation, not
   retrieval — and the thesis of vectorless RAG would not be supported by the
   data.
5. **Local-model judging noise.** A 7B judge will disagree with itself more than
   a frontier model does. Judge model and temperature are pinned and recorded in
   every run file so this is visible rather than inferred.
